# Security controls (database layer, Phases 1-3B)

| control | implementation | verified by |
|---|---|---|
| Tenant isolation | `restaurant_id` on every tenant table; RLS enabled+forced everywhere; policies use identity helpers derived from `profiles`; composite FKs make cross-tenant references impossible; `restaurant_id` immutable (trigger) and not client-writable (column grants) | `02_tenant_isolation`, `10_idor_bola` |
| No client-trusted claims | tenant/role/permissions never read from JWT custom claims | helpers in migration 0004 |
| Authorization | editable role→permission matrix (`role_permissions`, `role_station_access`) as UX layer; RLS/RPC as ceiling; no escalation through `fn_update_role_permissions` / `fn_change_user_role` | `03_integrity`, `11_role_escalation`, `15_immutability_audit` |
| Authentication methods | **tenant_admin and platform admins: Supabase Auth email + password (MFA-capable), never PIN. Non-admin staff: server-verified PIN.** `profiles.auth_method` ('password'/'pin') is forced consistent with the role by trigger; PIN staff must have a synthetic non-routable email (`*.staff.cafeos.invalid`), admins a real one; `profile_secrets` rows are rejected by trigger for admins/platform admins; PIN RPCs return the same result for admins as for unknown accounts; promotion deletes the PIN secret, demotion requires a new PIN; `fn_user_auth_method` lets an Auth hook block password login for PIN-only staff | `04_auth_methods` |
| PIN secrecy and lockout | the DB never sees a raw PIN: Edge Functions send `HMAC-SHA256(pin, PIN_PEPPER)`, stored as bcrypt in `profile_secrets` (RLS on, no policies, no client privileges); `fn_verify_pin` row-locks the secret first (concurrent guesses are serial); counter never decays on lock expiry (reset only by success or `fn_reset_pin_lockout`); lock 3rd failure 15 min / 6th 1 h / 9th 24 h, every later failure re-locks; locked/inactive/unknown/wrong all answer `{"status":"invalid"}`; weak-PIN policy (4 digits, 6 for the 'Cashier' role: the documented user-decided exception, see auth-flows.md; no repeated/sequential PINs) in the Edge Functions where the raw PIN is visible; `profile_secrets.pin_length` + `fn_pin_length_for_role_name` keep stored secrets consistent with the role | `04_auth_methods`, `19_pin_hardening`, `scripts/db/race-tests.sh` (60 concurrent guesses => 3 failures) |
| Platform/tenant boundary | `platform_admins` is a separate table; platform_super_admin is not derivable from `profiles`; platform tables are written only through aal2 platform RPCs (0030); suspension/reactivation/cancellation audited in `admin_audit_log`; see "Two portals" | `03_integrity`, `11_role_escalation`, `15_immutability_audit`, `02_tenant_isolation`, `10_idor_bola` |
| Tenant suspension | suspended/cancelled resolve to no tenant (no read/write); past_due read-only; RPCs call `fn_tenant_status_guard` | `02_tenant_isolation`, `10_idor_bola` |
| Immutability | triggers (fire for service_role and the owner too) on `audit_logs`, `admin_audit_log`, `payments`, `stock_movements`; closed `day_sessions` frozen and never deleted; **closed-day guard** (`fn_guard_closed_day`, `FOR SHARE` on the day row, so it serialises with the close) on orders, order_items, payments, stock_movements, vouchers, installments (only collection columns, against an open-day payment), table_sessions, customer_sessions (status/last_seen_at only); closed-day expenses frozen; service_role has no TRUNCATE/REFERENCES/TRIGGER and no write privilege on the audit tables | `03_integrity`, `11_role_escalation`, `15_immutability_audit` |
| Audit | row audit trigger (`fn_audit_row`, secrets stripped, changed columns only) on config domains, roles, matrix, profiles, menu, restaurants, QR, days, expenses; event audit via `fn_write_audit(event, record, restaurant?)`: **no actor parameter, the actor is only `auth.uid()`** (null = system), a tenant user can only write its own tenant, nobody (not even service_role) can EXECUTE it directly; row audit also on ingredients, recipe_lines, tables, vouchers, installments; `admin_audit_log` rows (`fn_audit_admin_row`) for plans, subscriptions, platform_invoices, platform_admins; no INSERT grant to any client or service_role | `03_integrity`, `11_role_escalation`, `15_immutability_audit` |

| Privilege hygiene | default privileges: no PUBLIC/anon/authenticated/service_role EXECUTE on future functions (`alter default privileges for role postgres revoke execute ... from public`, canary test in `18_*`); `fn_err` not anon; only explicit grants (migrations 0009+); sensitive columns (token hashes, stock columns, system flags) excluded via column grants; internal functions have no client EXECUTE | `03_integrity`, `11_role_escalation`, `15_immutability_audit`, `04_auth_methods` |
| Secrets in data | branding validated by CHECK (hex colours, tenant-scoped storage path, no URLs/base64); `menu_items.image_path` must be `restaurants/<own id>/...` | `03_integrity`, `11_role_escalation`, `15_immutability_audit` |
| Adversarial coverage | `supabase/tests/database/`: `10_idor_bola` (every tenant table + every UUID RPC, existence-oracle checks, byte-level snapshots), `11_role_escalation`, `12_platform_boundary`, `13_security_hygiene` (catalog-driven: definer search_path, EXECUTE allowlists, RLS enabled+forced, secrets, Realtime), `14_dynamic_domains`, `15_immutability_audit`, `16_tenant_status` | all of the above |

| Kiosk devices | `kiosk_devices` (hash-only token, no client grant on it, RLS forced, audited without hash); `fn_register_kiosk` / `fn_revoke_kiosk` / `fn_list_kiosks` (`kiosks.manage`); service-only `fn_kiosk_context` / `fn_kiosk_roster` / `fn_kiosk_tile_eligible`; roster = active non-admin 4-digit PIN staff only, tiles carry id/name/role/colour/icon; unknown/revoked/mismatch/suspended identical | `26_kiosk_devices`, `tests/unit/kiosk-logic.test.ts`, kiosk-terminals.md |
| Tenant host | `<slug>.cafeos.et` resolved by `_shared/host.ts`; reserved subdomains equal in TS and DB; CORS wildcard limited to one valid non-reserved label; Origin slug must match the body slug | `tests/unit/tenant-host.test.ts`, `26_kiosk_devices`, tenant-routing.md |
| Single session + forced PIN change | `fn_staff_has_active_session` (auth.sessions, 2 h freshness window, PIN-eligible staff only) and `fn_staff_login_blocked` are service-only; blocked login answers like a wrong PIN; `profile_secrets.must_change_pin` makes `has_permission` / `has_station_access` / `current_station_ids` answer nothing (tenant_admin exempt); after the change the account waits for tenant_admin approval (maker-checker, 0024: `fn_pin_restricted` is the single predicate; `pin_change_pending`; `fn_approve_pin_change` / `fn_reject_pin_change` need `users.manage` + a real authenticator (aal2 and a non-PIN account, 0026/0027), never the subject, identical `not_found` for unknown/foreign/not-pending; `fn_complete_forced_pin_change` service-only; `fn_list_pending_pin_changes` tenant-scoped); cleared by approval or an admin-set `fn_set_user_pin` (`pin-change` Edge Function also revokes other sessions); `user_notifications` recipient-only select, no client writes, read via `fn_mark_notification_read` | `27_single_session_forced_pin_change`, `28_pin_change_approval`, `scripts/db/race-tests.sh` (SS1), `tests/unit/pin-change-logic.test.ts`, `tests/unit/pin-login-logic.test.ts` |
| Session timers (0025) | per-tenant inactivity timers in `restaurant_session_settings` (1:1, RLS forced, member SELECT only, no client write grant, CHECK 5 <= warning < signout <= 900, signout >= 15, PIN pad 15..300); changed only by `fn_update_session_timers` / `fn_reset_session_timers` (`settings.session_timers`, aal2 (0026), writable tenant, `invalid_input` + field, audit with old/new); read by every member (also while PIN-restricted) via `fn_get_session_timers` / session context; kiosk gets only `pin_pad_idle_seconds` of the token's tenant via service-only `fn_kiosk_terminal_bootstrap`; the Edge Function re-validates (15..300, else 60). The timers are client UX/hygiene: the server session limits (JWT expiry, single-session window) stay the authority | `29_session_timer_settings`, `tests/unit/kiosk-logic.test.ts` |
| Mandatory aal2 (0026) | `fn_require_aal2()` (internal, no client EXECUTE) raises `mfa_required` unless the JWT carries `aal = 'aal2'`; unlike `fn_require_step_up()` it has no pass for an account with no verified factor, so PIN-only staff holding the permission cannot act. 0028 (finding L1): it ALSO requires a verified `auth.mfa_factors` row for `auth.uid()` (same predicate as `fn_require_step_up`: `user_id = auth.uid() and status = 'verified'`), so a still-valid aal2 token of an account whose authenticator was removed is refused on the next call instead of staying valid up to `jwt_expiry`; residual: a token issued at aal2 stays aal2 while the factor exists, until it expires. 0027 (finding H1): it ALSO raises `mfa_required` when the caller's profile (`id = auth.uid()`) has `auth_method = 'pin'` (or no profile exists), because a PIN staff member holds a real GoTrue session and can enrol TOTP through `auth.mfa.enroll` / `challengeAndVerify` to obtain an aal2 JWT; aal2 therefore requires `auth_method <> 'pin'`. The "fresh code" asked before removing an authenticator in the SPA is a UX guard only (M1), never a security control. Used only by the PIN-change decision (`fn_approve_pin_change` / `fn_reject_pin_change` via `fn_decide_pin_change`) and the session-timer writes (`fn_update_session_timers` / `fn_reset_session_timers` via `fn_store_session_timers`); order tenant guard -> permission -> aal2 -> validation, so an aal1 caller learns nothing about ids or input validity. Only a tenant_admin with an enrolled authenticator, on an aal2 session, can perform these: `fn_guard_profile_auth_method` ties `auth_method = 'password'` to the tenant_admin role, so a `users.manage` / `settings.session_timers` grant to any other role is inert for these actions (fails closed). All other step-up RPCs keep `fn_require_step_up()` | `28_pin_change_approval`, `29_session_timer_settings`, `10_idor_bola`, `13_security_hygiene` |
| Menu and inventory (0029) | menu / recipe / ingredient / stock commands are definer RPCs (tenant from identity, `menu.manage` / `inventory.adjust` / `inventory.receive`, closed-key patches, numeric validation without silent rounding, `not_found` for foreign ids, event audit); **one ledger writer** (`fn_post_stock_movement`: ingredient row lock, open business day required => `day_closed`, never below zero => `insufficient_stock`), so `ingredients.stock = sum(stock_movements.qty_delta)`; corrections are compensating `reversal` rows (once only); retryable commands (`fn_receive_stock`, `fn_adjust_stock`, `fn_reverse_stock_movement`) use tenant-scoped idempotency keys with a payload hash; **RPC-only writes**: no client INSERT / UPDATE / DELETE privilege on `menu_items`, `recipe_lines`, `ingredients` (SELECT under RLS only); **stock step-up** (`fn_stock_step_up`) on receive, adjust, reversal and initial stock: `|qty| * cost >= threshold` or (cost 0 and `|qty| >= threshold`), threshold per tenant (`restaurants.stock_stepup_threshold`, default 5000 ETB, 100..1000000, changed only by `fn_set_stock_stepup_threshold` with `settings.manage` + aal2, audited old/new); changing `cost_per_unit` of an ingredient with movements needs step-up; idempotency key format checked before any lookup / lock; ledger writer pre-checks the numeric(12,3) ceiling (`invalid_input`, never a raw overflow); recipe / reactivation take `FOR SHARE` locks on the ingredients (no deactivated ingredient behind an active item); unit locked by movements or recipe lines; `duplicate_name` only for the tenant name key; recipe consumption helpers are internal (Phase 4 callers) and derive the tenant from the order row; private `menu-images` bucket (2 MiB, png/jpeg/webp) with tenant-prefix, case-sensitive Storage policies (a referenced image can be neither renamed nor deleted), DB `image_path` must be an existing object under `restaurants/<own id>/menu/` | `30_menu_inventory`, `31_menu_inventory_adversarial`, `13_security_hygiene`, `24_coverage_gaps` |
| Two portals (0030 / 0031, §34A) | **Platform Admin Portal**: every platform RPC (`fn_platform_*`, `fn_suspend_tenant`, `fn_reactivate_tenant`, platform path of `fn_provision_tenant` and of the invitation RPCs) passes `fn_platform_guard()`: active `platform_super_admin` + JWT `aal2` + a verified factor the account still owns, **no GUC opt-out**; every platform write appends a semantic `admin_audit_log` row (and an `audit_logs` event of the tenant concerned, actor_type `platform_admin`); platform tables are RPC-only for clients (INSERT / UPDATE / DELETE revoked on `plans`, `subscriptions`, `platform_invoices`, `platform_admins`); tenant data visible to the platform = tenant metadata, subscription / billing and AGGREGATE usage counters (`fn_tenant_usage`: counts and byte sums only, never a row, name or id of an operational record); a Super Admin is added only by ops (`fn_ops_register_platform_admin`, service_role). **Tenant Portal**: roles / users / restaurant writes are RPC-only (INSERT / UPDATE / DELETE revoked on `roles`, UPDATE on `profiles` and `restaurants`) with permission checks, step-up (aal2 for money settings), closed-key patches, structured errors (`role_in_use`, `system_role_protected`, `permission_escalation`, `staff_limit_reached`, ...) and event audit. **Separation**: a platform admin has no profile, so every tenant policy and RPC resolves to nothing / `permission_denied`; tenant users get `permission_denied` from every platform RPC; one auth user is a platform admin OR a tenant profile, never both (guards on both tables share a per-user advisory lock: the concurrent dual-identity race existed before 0030 and is now closed) | `34_portal_separation` (catalog-driven sweeps over EVERY tenant / platform RPC, zero-row proof over EVERY operational table), `32_platform_portal`, `33_tenant_portal`, `20_platform_hardening`, `12_platform_boundary`, `13_security_hygiene`, `scripts/db/race-tests.sh` (3B) |
| Tenant Admin invitation (0030) | `tenant-admin-invite` Edge Function: authorisation by `fn_prepare_tenant_admin_invitation` AS THE CALLER (platform: `fn_platform_guard`; tenant_admin: tenant guard + `is_tenant_admin` + `fn_require_aal2`; tenant from identity), service role only for `auth.admin.inviteUserByEmail` / `deleteUser` and the service-only `fn_attach_tenant_admin_invitation` / `fn_abort_tenant_admin_invitation`; reservation refuses any existing Auth account (`email_in_use`: never re-bind an account, platform admins included), synthetic `.invalid` identities and a full staff quota; one pending invitation per e-mail platform-wide; resend rate limited in SQL (60 s, 5 sends); revoke hands back only a never-confirmed user for deletion; binding happens only in `fn_accept_tenant_admin_invitation()` by the invitee itself (confirmed e-mail equal to the invitation, not expired, tenant not suspended / cancelled, no existing profile / platform admin) and creates a `tenant_admin` profile with `auth_method = 'password'` (never PIN); every step audited | `35_tenant_admin_invitations`, `tests/unit/tenant-admin-invite-logic.test.ts`, `deno check` |
